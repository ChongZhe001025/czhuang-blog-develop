能檢查 Kubernetes 事件的自動化系統，不代表它也應該被允許修改叢集。提出動作前，系統必須確認輸入有效、目標受到支援，而且動作符合明確的風險政策。

FluxSeer RCA 的開發透過 Runtime Validation、風險規則與面向使用者的情境，探索這些安全邊界。目標是儘早拒絕模糊或不受支援的請求，並讓操作人員看得見證據與判斷結果。

## 調查或執行前先驗證

驗證應放在 Runtime 邊界，不應只依賴文件或使用者介面。即使請求經過有效 API Endpoint，內容仍可能格式錯誤。至少要驗證：

- 目標存在，且其 Kind 受到支援；
- 請求的調查模式受到支援；
- Data Source 已設定且可連線；
- Query Template 符合所選 Adapter 的格式；
- 必要欄位與安全設定符合 API Contract。

若請求未通過其中一項檢查，應回傳結構化原因，並在產生調查結果或動作前停止。這可避免下游元件猜測使用者的真正意圖。

## 明確定義風險政策

風險規則將營運邊界轉為可檢視的政策。規則應明確指出：檢查哪個訊號、適用哪些目標類型、如何判定嚴重程度，以及提出的修復動作是允許、封鎖還是需要核准。

預設行為很重要。如果規則沒有明確匹配，或必要 Data Source 無法使用，系統不應默默擴大權限。較安全的行為是回傳可解釋的「不符合執行條件」結果，並保留導致該判斷的證據。

每個提議的動作都應能追溯：

```text
使用者請求
  -> 驗證目標與資料來源
  -> 產生有證據支持的發現
  -> 套用匹配的風險規則
  -> 判斷執行資格／是否需要核准
  -> 執行受限動作（若獲准）
  -> 記錄結果
```


分析結果與動作執行結果是兩回事。可信的根因判斷本身並不代表已獲得變更授權。

## 不只測試成功路徑，也要測試拒絕情境

Data Source 驗證工作記錄了 12 個情境，且全數通過。涵蓋無效目標、不支援的調查模式與目標 Kind、無效 Query Template，以及無效規格。這些負向測試很重要，因為不安全行為常出現在輸入不完整或功能不受支援的邊界。

穩健的測試矩陣不應只檢查 HTTP Status。每個無效情境都要確認回應指出失敗欄位或功能、沒有建立任何 Action，而且沒有任何寫入抵達叢集。

也要測試成功的唯讀路徑：系統選取指定資料來源、回傳附有來源脈絡的證據，並在報告中呈現不確定性。使用者測試則要確認操作人員看得懂請求為何被接受或拒絕。

## 將 Action 生命週期與執行資格分開

Action 符合執行條件後，仍可能需要核准、執行、觀察與過期處理。開發對話將 AgentAction TTL 視為規劃中的生命週期改善；在實作與測試完成前，應將它描述為設計考量。

這種區分可以避免常見的安全誤解：把「Action 通過驗證」當成「Action 已完成而且沒有風險」。系統需要明確狀態、受限的執行範圍，以及可查閱的執行紀錄。

## 實用的安全原則

- 目標身分、資料來源或政策判斷有歧義時，採取 Fail Closed。
- 將調查證據與修改叢集的權限分開管理。
- 使用結構化驗證錯誤，指出被拒絕的功能或欄位。
- 測試接受請求的情境，以及所有重要拒絕情境。
- 記錄產生判斷的政策與輸入。
- 風險較高的動作應限制執行範圍，並保留人工檢視界線。
- 不要根據有限的驗證矩陣宣稱全面支援 Kubernetes。

安全的自動化來自可執行、可測試的限制。系統的價值不在於永遠回答「可以」，而在於說明它掌握了什麼、還無法確認什麼，以及某個動作為何能執行或必須拒絕。
