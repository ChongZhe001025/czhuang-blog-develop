資料庫 Migration 不應在 Import 指令成功結束時就算完成。只有新 Schema 保留舊紀錄的語意，而且應用程式能正確使用遷移後的資料，才算完成。

FinTrack Migration 工作一開始刻意暫停寫入：先檢查舊備份與 Development Database Schema，釐清欄位對應後才匯入。後續對話才開始使用本機副本與進行匯入。這段過程示範了如何將探索階段與資料變更分開。

第一次檢視目標資料時，找到一個 Ledger、七個 Category 與一個 Profile；Transaction、Budget、Fixed Expense 與 Ledger Rebase Collection 都是空的。舊 Archive 被還原到本機暫時使用的 MongoDB 供檢查。當時的要求明確為唯讀：不得還原或匯入 Development Database。這提供了具體的遷移前狀態，也清楚保留本機檢查與遠端寫入之間的邊界。

## 階段一：唯讀盤點兩邊 Schema

先確認來源與目標版本、Collection 或 Table、欄位型別、識別碼與關聯。應比較具代表性的紀錄，不要假設欄位名稱相同就代表語意一致。

匯入前先建立對照表：

| 來源概念 | 目標概念 | 轉換方式 | 待確認事項 |
|---|---|---|---|
| 舊識別碼 | 新識別碼 | 保留或重新指派 | 是否有外部參照？ |
| 日期或時間戳 | 新時間欄位 | 明確正規化 | 由哪個時區定義日期？ |
| 選填欄位 | 新預設值或 Nullable 欄位 | 套用已文件化的規則 | 缺少欄位是否有意義？ |

若無法有把握地映射欄位，先暫停並詢問產品負責人。猜測可能會讓交易默默連到錯誤帳戶，或改變交易日期。

## 階段二：保護來源並讓匯入可重複執行

將原始備份設為不可變，並使用獨立副本進行操作。記錄來源版本與預期紀錄數量。匯入流程應能在 Staging Database 重複執行，而不會產生重複紀錄。Dry Run 應回報預計新增、更新、略過或拒絕的紀錄數。

在 Importer 中明確設定允許使用的 Environment，並在任何寫入前印出選取的 Database 名稱。Migration 對話一開始的「不要匯入」要求正是重要的保護措施：探索指令不能默默變成還原指令，本機 Mongo Restore 也不可重用 Development Connection String。

匯入流程應明確處理：

- 識別碼保留與衝突；
- 日期及數值轉換；
- 必填欄位與預設值；
- 關聯建立順序；
- 不符合已核准對照規則的紀錄。

不要把破壞性清理併入第一次 Migration。若需要取代資料，先定義備份與回復程序。

## 階段三：核對匯入結果

匯入後，按 Entity 與相關狀態比較來源和目標筆數，再於資料庫與應用程式層驗證具代表性的紀錄：

1. 確認紀錄筆數與識別碼。
2. 抽樣比對重要欄位及關聯。
3. 檢查日期、貨幣精度與選填值。
4. 透過應用程式 API 與 UI 開啟遷移後的資料。
5. 驗證使用遷移欄位的報表與固定週期交易行為。
6. 記錄遭拒紀錄，並在宣告完成前處理完畢。

彙總筆數可以揭露資料遺失，卻無法發現錯誤帳戶參照或日期偏移。核對必須包含總量與語意檢查。

## 將不同階段分開管理

唯讀 Schema 盤點、本機備份副本與目標資料 Import 是風險不同的操作。第一次 Migration 請求明確要求欄位意義釐清前先不要匯入。後續 Import 對話代表工作持續進行，但每次 Migration 仍應記錄自己的輸入、Mapping 版本與驗證結果。

後續本機複製／匯入工作能證明 Migration 實作繼續進行，但早期目標資料筆數不是匯入後的核對結果。不能將來源 Archive 與那些當時為空的 Collection 比較，並聲稱它們是匯入後測量值。可公開的 Migration 報告需要有時間戳記的前後筆數表、抽樣關聯，以及該次執行的應用程式層檢查。

採用分階段流程：

```text
備份 -> Schema 盤點 -> 核准欄位對照 -> Dry Run
     -> Staging 匯入 -> 資料核對 -> 應用程式檢查
     -> Production Plan 與回復點 -> Production 匯入
```


欄位意義仍在探索時，絕不要使用 Production Database Connection。

## Migration 完成檢查清單

- 原始來源備份已保留並完成 Checksum。
- 目標 Schema 與 Mapping 規則已記錄。
- 模糊欄位已有明確決策。
- Import 可重複執行或安全續跑。
- 紀錄總數與抽樣資料均核對完成。
- 核心應用程式流程能正常使用遷移資料。
- Production Import 已具備回復點與負責人核准。

FinTrack Migration 的核心原則很簡單：先檢查、確認語意，再匯入。驗證必須證明應用程式仍然理解資料，而不只是資料庫接受了寫入。
