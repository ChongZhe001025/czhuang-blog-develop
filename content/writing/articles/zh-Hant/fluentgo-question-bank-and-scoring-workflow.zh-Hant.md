FluentGO 延續自較早的 GoTOEIC 專案。開發過程從 Runtime 與資料儲存問題，逐步擴展為完整的學習流程：遷移持久化層、將評分移至後端、匯入題目資料、分類文法題型，並改善推薦功能。

本文將這些演進視為同一個產品的發展，而不是把重新命名當成另一個應用程式。

## 1. 穩定服務邊界

早期工作排查了容器啟動、受保護資源回傳 `401`，以及應用程式是否仍使用 MongoDB。後續方向是將服務轉向 PostgreSQL，並讓評分由後端負責。

目前專案邊界是 Go API 加上 PostgreSQL；API 啟動時會建立 Schema。題目內容與作答評分由伺服器處理，Client 傳送答案並呈現回傳的作答狀態。這避免每個瀏覽器畫面都維護一份獨立評分邏輯。

讓後端負責評分有兩個好處：規則只有單一可信來源，而且不論從哪個畫面開始練習，Client 都會收到一致結果。API Contract 應明確定義送出的答案、題目識別碼與回傳分數。

## 2. 將題庫匯入設計成流程

題庫工作包含匯入 JSON、清理解析結果與整理圖片資產。匯入應是一連串驗證步驟，而不是只執行一次的腳本：

```text
來源 JSON
  -> 解析並驗證
  -> 正規化題目與答案欄位
  -> 分類題目類型
  -> 確認資產參照
  -> 寫入資料庫
  -> 比對匯入筆數與抽樣紀錄
```


對格式錯誤的紀錄提供明確原因並予以拒絕。可能的情況下保留穩定的來源識別碼，讓修正後重新匯入時可以更新題目，而非產生重複項目。也要確認每題都有答案，且引用的圖片可以載入。

專案提供可重複執行的匯入與涵蓋率報告指令：

```sh
make import-questions
make question-coverage-report
```


匯入後請比較接受與拒絕的筆數，並抽查代表性紀錄。資料庫寫入成功，不代表答案、文法標籤或媒體 URL 一定正確。

## 3. 讓文法分類真正幫助學習者

分類工作分析了 TOEIC 文法題型，後續也進一步調整題目推薦。分類應服務學習體驗，而非只是在資料庫新增標籤。先定義小而容易檢視的分類方式，再用代表性題目驗證，之後才用它建立練習題組。

若題目可能屬於多個類別，可設定主要類別並加上次要標籤，或將題目放進人工檢視佇列。不要對解析品質不佳的結果逕自給予確定分類。

## 4. 讓評分具決定性且可測試

後端評分服務應接受穩定的題目識別碼與學習者選擇的答案，再回傳 Client 能一致呈現的結果。測試情境應涵蓋：

- 正確與錯誤答案；
- 空白或格式錯誤的送出內容；
- 重複送出；
- 缺少答案欄位的題目紀錄；
- 一次練習中的分數彙整。

之後推薦邏輯即可使用已驗證的題目分類與學習者作答結果。初期推薦規則應保持可檢視，才能說明某題為何被選入。

文件化的 Demo 流程會建立可重現的練習資料，並在同一個 Runtime 中執行建立作答階段、提交答案、結束作答、記錄事件、產生指標資料、更新複習佇列與更新推薦等步驟。這讓驗證範圍超越單次分數回應。只有實際執行指令並保存輸出後，才能將它描述為已驗證的執行流程。

## 5. 驗證完整學習路徑

專案工作涵蓋資料庫變更、題目匯入、前端行為、Hook 相依修正、正式環境設定與外部連線。具意義的端到端檢查，應跟著學習者從載入練習題組、送出答案、取得後端評分，一直到確認結果反映在下一次推薦中。

同時核對匯入前後的題目數量、抽查各文法分類的題目，並確認正式環境能載入引用的媒體資源。

## 這段演進呈現的工程價值

最有價值的技術脈絡，是題庫從單純的題目集合演進為學習流程：結構化內容、由後端負責評分、題型分類與推薦。文章應區分已實作行為與仍在調整的推薦想法；沒有學習者或成效資料時，不應宣稱學習表現已提升。
