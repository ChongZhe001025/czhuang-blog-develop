伺服器以 UTC 顯示時間、使用者以當地時間閱讀時，即使兩個時鐘描述的是同一個時間點，畫面上的時鐘仍可能看起來不一致。排查 FinTrack 伺服器時間時就遇到這個情況：容器中的 UTC 時間比台灣時間晚數小時，但時區偏移量正好能解釋差異。

更棘手的是固定週期交易。它混合了兩種不可互換的時間概念：全球時間軸上的某個瞬間，以及使用者時區中的日曆日期。

## 先區分時鐘偏差與時區顯示

調整主機時鐘前，先將時間轉換至相同時區比較。如果伺服器回報 `2026-04-09 23:54 UTC`，在台北約為 `2026-04-10 07:54`。日期跨日是因時區偏移，不代表伺服器時間落後。

機器彼此傳遞的時間戳與日誌，盡可能使用 UTC；在應用程式邊界再轉成使用者時區，用於顯示與商業日曆計算。更改伺服器系統時區可能改變排程工作與日誌解讀方式，卻沒有修正底層的日期模型。

## 分別建模時間瞬間與日曆日期

「更新時間」這類稽核時間戳代表一個特定瞬間，適合以時間點儲存。某個本地日期應執行的固定週期交易則是一條日曆規則。若應用程式太早將日期轉成 UTC，午夜就可能落在前一天或後一天。

在 Go 中，應明確指定商業時區：

```go
loc, err := time.LoadLocation("Asia/Taipei")
if err != nil {
    return err
}

localStart := time.Date(year, month, day, 0, 0, 0, 0, loc)
localEnd := localStart.AddDate(0, 0, 1)

queryStart := localStart.UTC()
queryEnd := localEnd.UTC()
```


資料庫查詢應使用半開區間 `[queryStart, queryEnd)`。它能涵蓋本地日期中的所有時間點，不必依賴脆弱的 `23:59:59.999` 數值。

固定週期交易的下一次發生日，應根據其日曆規則與時區產生，而不是將前一個 UTC 時間戳加上固定秒數。每個月的天數不同，採用日光節約時間的地區也可能有不規則的日長，而且全球各地的本地午夜並非固定時差。

FinTrack 後續實作將 Ledger 作為時區邊界。`Ledger.Timezone` 儲存 IANA 時區；固定交易隸屬於 Ledger，因此不重複儲存時區欄位。時區為空的既有 Ledger 會回填為 `Asia/Taipei`，與先前應用程式行為一致。這次回填不會強制重新計算既有的 `nextRunAt` 值。

```go
loc, err := config.LocationForTimezone(ledger.Timezone)
if err != nil {
    return err // invalid IANA timezone is rejected at the ledger boundary
}
nextRunAt := calculateNextRunAt(dayOfMonth, from, loc).UTC()
```


排程器仍以 `time.Now().UTC()` 比較已儲存的 UTC 時間點。建立交易時，則使用 Ledger 時區中的午夜，再把該時間轉換為 UTC。若每月指定日期為 31 日，文件化的行為是在較短月份中調整為該月最後一天。

## 計算下一次發生日之前先驗證日期

API 應拒絕不可能的日期，不要默默正規化。例如 2 月 31 日必須通過驗證並回報錯誤。每月發生的週期規則也要定義：遇到少於指定日期的月份時，是調整至最後一天、略過該月，還是套用另一條明確產品規則。

儲存的週期資訊必須足以重現使用者意圖：

- 週期規則；
- 相關的本地日曆日期或每月日期；
- 用來解讀該日期的時區；
- 若系統會建立具體發生項目，也要記錄其 UTC 時間點。

不要事後依賴伺服器目前的時區設定推測使用者時區。

## 測試造成混淆的邊界情境

測試午夜、月底、閏日與時區轉換。也要一起測試建立、編輯與列表流程：日期可能正確儲存卻在畫面顯示成錯誤日期，也可能顯示正確但查詢時被排除。

實作也將交易列表與報表的日期邊界改為依所選 Ledger 的時區計算，並使用半開區間 `occurredAt >= startUTC && occurredAt < endExclusiveUTC`。統計、類別統計、比較、年度報表與預算狀態都遵循相同 Ledger 日曆。`ledgerId=all` 的查詢仍退回使用應用程式時區，因為合併不同商業日曆的 Ledger 需要依 Ledger 分別彙整。

伺服器時間調查確認 `2026-04-09 23:54 UTC` 與台北約 `2026-04-10 07:54` 是同一個瞬間。後續測試涵蓋 UTC、美國太平洋時區、日光節約時間轉換、31 日在月底的調整，以及排他性的查詢結束時間。專案紀錄顯示 `go test ./...`、指定的 Ledger／固定交易 UI 測試，以及 Client Build 均通過。固定交易排程的整合流程仍是後續工作，應明確保留此限制。

## 精簡檢查清單

- 欄位表示的是時間瞬間，還是日曆日期？
- 哪個時區定義固定週期使用者的一天？
- 是否以一致方式轉換日期邊界？
- 日期型輸入是否在轉換前驗證？
- 每月週期遇到較短月份時如何處理？
- API、資料庫查詢與 UI 測試是否涵蓋午夜與月底？

明確定義時間語意，才能避免日期偏移進一步造成重複交易、報表漏列或稽核紀錄難以理解。
